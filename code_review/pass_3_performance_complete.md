# Performance Review — complete (cross-cutting)

## Summary

Across all three layers the individual-layer reviews found no algorithmic disasters, and the same conclusion holds end-to-end. The cross-cutting picture adds three concrete findings that are invisible from within any single layer. First, `visibleObjects()` is traversed twice per WebSocket turn because the server explicitly calls it and then calls `availableActions()`, which re-calls `visibleObjects()` internally — a redundancy only visible by reading both `WebSocketDeckerController.kt` and `Decker.kt` together. Second, the available-actions list is built in full by game logic, immediately partially discarded by the server, and then broadcast in its entirety to all connected sessions (including observers who cannot act), inflating every `StateMessage` payload and cascading into unnecessary React re-renders for non-controller clients. Third, `SWAP_MEMORY` and `LOCATE_DECKER` entries are unconditionally generated by game logic and unconditionally stripped by the server on every turn, making them permanent waste in the action-building pipeline. Everything else — the per-layer allocations, the CSS repaint cost, the double JSON parse — has been captured in the individual reviews and introduces no additional cross-layer concerns beyond those already described.

## Findings

### [HIGH] `visibleObjects()` traversed twice per WebSocket turn
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:43–44  
and src/main/kotlin/com/shadowrun/matrix/decker/Decker.kt:155

**Issue:** `WebSocketDeckerController.action()` calls `decker.visibleObjects()` on line 43 to build the state payload, then immediately calls `decker.availableActions()` on line 44. Inside `availableActions()`, `addGridSystemActions()` calls `visibleObjects()` a second time (Decker.kt:155) to enumerate IC programs. On a host location (`OnHost`), each `visibleObjects()` call allocates a `buildList` and iterates five separate collections (`nodes`, `icPrograms`, `dataFiles`, `remoteDevices`, `connectedHosts`). The result of the second call is used only to `filterIsInstance<MatrixObject.IcProgram>()`, allocating yet another filtered list. Neither call from within `addGridSystemActions()` produces anything that differs from the first call already stored in `visibleObjects` on the server side. This redundancy is invisible from within either layer alone.

**Recommendation:** Pass the already-computed visible-objects list into `availableActions()` as a parameter, or cache it as a `val` before building the actions list:
```kotlin
val visibleObjects = decker.visibleObjects()
val availableActions = decker.availableActionsFrom(visibleObjects)
    .filterNot { ... }
```
In `Decker.kt`, change `addGridSystemActions()` to accept the pre-built list:
```kotlin
private fun MutableList<AvailableAction>.addGridSystemActions(visible: List<MatrixObject>) {
    // ...
    visible.filterIsInstance<MatrixObject.IcProgram>()
        .forEach { add(AvailableAction.Operation(SystemOperation.ANALYZE_IC, it)) }
}
```
This eliminates the second `buildList` allocation and the redundant five-collection traversal on every turn.

### [MEDIUM] Full `availableActions` list broadcast to all roles, inflating every payload and triggering UI re-renders for non-controller clients
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:62–68  
and src/main/kotlin/com/shadowrun/matrix/server/SessionRegistry.kt:142  
and frontend/src/components/ActionsPanel.tsx:56–58

**Issue:** The `StateMessage` built in `WebSocketDeckerController.action()` embeds the full `availableActions` list in `stateBase` before calling `broadcastWithRoles`. `broadcastWithRoles` then serializes this payload once per role (`OBSERVER`, `REGISTERED_DECKER`, `ACTIVE_CONTROLLER`) and sends it to every connected session. Observers and registered deckers who are not the active controller receive the complete action list even though the server unconditionally rejects any `ActionCommand` they send. On a host with 5 IC programs, 10 data files, and 5 remote devices the action list reaches approximately 50 entries. Each entry is a separate serialized object; the JSON payload for the non-controller broadcast is meaninglessly large. On the UI side, `ActionsPanel` runs `useEffect(() => { setCardStates({}) }, [actions])` on reference change; since the `STATE` reducer always replaces `gameState` by reference, `actions` is always a new array for every connected client including observers, causing the card-state wipe to fire on every server push for every session. This cross-layer cascade — game logic builds → server broadcasts to all → UI re-renders all — is only visible by tracing the pipeline across all three files.

**Recommendation:** Include `availableActions` only in the `ACTIVE_CONTROLLER` payload; send an empty list for the other two roles:
```kotlin
val stateBase = StateMessage(
    role = SessionRole.OBSERVER,
    decker = decker.toDto(),
    visibleObjects = visibleObjects.toDto(),
    availableActions = emptyList()          // filled per-role below
)
val actionsDto = availableActions.toDto()
// In SessionRegistry.broadcastWithRoles, or inline:
val byRole = mapOf(
    SessionRole.ACTIVE_CONTROLLER to MatrixJson.encodeToString(stateBase.copy(role = SessionRole.ACTIVE_CONTROLLER, availableActions = actionsDto)),
    SessionRole.REGISTERED_DECKER to MatrixJson.encodeToString(stateBase.copy(role = SessionRole.REGISTERED_DECKER)),
    SessionRole.OBSERVER          to MatrixJson.encodeToString(stateBase.copy(role = SessionRole.OBSERVER)),
)
```
This also makes the UI fix from the per-part review (stabilising `ActionsPanel`'s effect dependency) unnecessary for non-controller clients, because their `actions` array will always be empty and stable.

### [MEDIUM] `SWAP_MEMORY` and `LOCATE_DECKER` actions built by game logic and unconditionally discarded by the server on every turn
**File:** src/main/kotlin/com/shadowrun/matrix/decker/Decker.kt:167, 174  
and src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:45–46

**Issue:** `addHostSystemActions()` in `Decker.kt` always appends `AvailableAction.Operation(SystemOperation.LOCATE_DECKER)` (line 167) and `AvailableAction.Operation(SystemOperation.SWAP_MEMORY)` (line 174) to the action list. `WebSocketDeckerController.action()` immediately filters both out via `filterNot { it is AvailableAction.Operation && it.operation in setOf(...) }` (lines 45–46). The server's own dispatch confirms they are permanently unsupported in this context (lines 233 and 305: "not supported via WebSocket"). Neither the object allocation in game logic nor the `setOf` + `filterNot` work in the server can ever produce a useful result. The `setOf` allocation was flagged in the per-part server review; the cross-cutting view shows the root cause is upstream in game logic.

**Recommendation:** Remove `LOCATE_DECKER` and `SWAP_MEMORY` from the `addHostSystemActions()` list in `Decker.kt` and delete the `filterNot` from `WebSocketDeckerController.action()`. If these operations must remain available for non-WebSocket callers (e.g. future programmatic or test use), add them back via a separate override parameter or a context flag, keeping the game-logic layer unaware of transport constraints.

### [INFO] `availableActions.toDto()` uses reflection per action; result serialized per role
**File:** src/main/kotlin/com/shadowrun/matrix/server/dto/AvailableActionDto.kt:66  
and src/main/kotlin/com/shadowrun/matrix/server/SessionRegistry.kt:142

**Issue:** `AvailableAction.toDto()` calls `it::class.simpleName` (reflection) for every `Operation` action that has a target. The per-part server review flagged this as INFO. The cross-cutting view adds one dimension: the DTO list is built once but the `StateMessage` containing it is then serialized once per connected session in `broadcastWithRoles` (per-part server review: up to 32 serializations per turn). The reflection cost is paid once during DTO mapping; the serialization cost is paid per session. After applying the MEDIUM fix above (pre-serialize by role, send empty actions to non-controllers), serialization drops to at most 3 invocations per turn regardless of session count, and the reflection cost is eliminated for the two non-controller payloads entirely. No additional action is needed beyond the two higher-severity recommendations; this entry documents the interaction.

## No Issues Found In

- The WebSocket frame parsing pipeline (`MatrixServer.kt` → `useWebSocket.ts`): the double-parse issue is a per-part concern; the cross-cutting framing adds nothing new — the two layers agree on their message contract through `types/messages.ts` and the contract is correctly mirrored.
- `StateMessage` fields other than `availableActions` (`decker`, `visibleObjects`, `role`): these are consumed correctly by all roles, correctly sized, and the DTO mapping is a single flat pass with no hidden cross-layer redundancy.
- Reconnect and session lifecycle paths: no cross-layer performance concerns; the reconnect token is a small string and the join handshake is a one-shot operation per session.
- Combat turn scheduling (`TurnCoordinator`, `GameContext`, `Game.kt`): the IC-action hot path and decker-action hot path are cleanly separated; no cross-layer redundancy introduced by the server orchestration.
- TypeScript type definitions (`frontend/src/types/messages.ts`): pure declarations; no runtime cost and correctly aligned with Kotlin DTO serialisation conventions.
