# Maintainability Review — complete (cross-cutting)

## Summary

Across all three layers the codebase is well-structured and consistent in most areas: sealed hierarchies map cleanly from game logic through server DTOs to TypeScript discriminated unions, the WebSocket message contract is fully typed on both sides, and the reducer pattern in the frontend is a good fit for the stateful connection. The dominant cross-cutting maintainability problem is that the TypeScript `SystemOperation` union type contains four phantom entries (`GRACEFUL_LOGOFF`, `LOGON_TO_HOST`, `LOGON_TO_LTG`, `LOGON_TO_RTG`) that correspond to dedicated DTO variants in the server layer and can never arrive as the `operation` field of an `Operation` DTO — creating a silent lie in the type definition that spans both the server DTO design and the frontend type file. A secondary cross-cutting concern is the triple-layer dormant interface for `inactivitySeconds`: present in both the Kotlin `ActionParams`, the TypeScript `ActionParams`, and wired into the controller dispatch, but never sent by the UI. A third concern is that the `ResultMessage.details` field acts as an untyped free-form string contract between the Kotlin result converters and the frontend `NarrativePanel`, meaning any format change on the server side silently changes what players see with no compile-time protection. Finally, a finding in the per-part server review incorrectly identified `AvailableActionDto.actionType` as redundant with the JSON discriminator `kind`; cross-cutting analysis shows they carry distinct game information.

## Findings

### [HIGH] TypeScript `SystemOperation` union contains phantom entries for dedicated DTO variants

**File:** `frontend/src/types/messages.ts:80`

**Issue:** The `SystemOperation` TypeScript union type includes `'GRACEFUL_LOGOFF'`, `'LOGON_TO_HOST'`, `'LOGON_TO_LTG'`, and `'LOGON_TO_RTG'`. In the server layer these actions are mapped to their own dedicated `AvailableActionDto` variants (`GracefulLogoff`, `LogonToHost`, `LogonToLtg`, `LogonToRtg`) and are never serialised as the `operation` field of an `Operation` DTO. The controller dispatch confirms this: `GracefulLogoff`, `JackOut`, and the four logon actions are handled by their own `when` branches before any `AvailableAction.Operation` case is reached (`WebSocketDeckerController.kt:125-141`). The TypeScript union therefore declares values that the `operation: SystemOperation` field of an `Operation` DTO can never hold. Any frontend code that switches over `SystemOperation` and adds cases for these four values produces dead branches, and a future developer scanning `messages.ts` for what the server can send is misled about the shape of the protocol.

**Recommendation:** Remove `'GRACEFUL_LOGOFF'`, `'LOGON_TO_HOST'`, `'LOGON_TO_LTG'`, and `'LOGON_TO_RTG'` from the `SystemOperation` type in `messages.ts`. Add a brief comment explaining that navigation actions have their own `AvailableActionDto` variants and do not appear as `Operation.operation` values, so the union stays intentionally smaller than the Kotlin `SystemOperation` enum.

### [HIGH] `LOCATE_DECKER` and `SWAP_MEMORY` are generated by game logic, filtered by the server, but present in the frontend type — three-layer dead code

**File:** `src/main/kotlin/com/shadowrun/matrix/decker/Decker.kt:167` and `src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:45` and `frontend/src/types/messages.ts:81`

**Issue:** `Decker.addHostSystemActions` adds both `SystemOperation.LOCATE_DECKER` and `SystemOperation.SWAP_MEMORY` to the available actions list (lines 167, 174). `WebSocketDeckerController.action` immediately filters them out before the `StateMessage` is sent to the client (lines 45–46). The TypeScript `SystemOperation` union includes both `'LOCATE_DECKER'` and `'SWAP_MEMORY'`. The result is a dead-code trail across all three layers: the game logic produces them, the server silently drops them, and the frontend type implies they are receivable. A developer working on any one layer in isolation sees apparently live entries; only the cross-layer view reveals they can never reach the UI.

**Recommendation:** Remove `LOCATE_DECKER` and `SWAP_MEMORY` from `Decker.addHostSystemActions` (they are unsupported by design), making the filter in the controller redundant and removable. Remove `'LOCATE_DECKER'` and `'SWAP_MEMORY'` from the TypeScript `SystemOperation` union, or add a comment marking them as never sent until implemented. This eliminates the three-layer inconsistency and makes the contract honest.

### [MEDIUM] `inactivitySeconds` is defined and wired across all three layers but never sent by the UI

**File:** `src/main/kotlin/com/shadowrun/matrix/server/dto/Messages.kt:53` and `frontend/src/types/messages.ts:14` and `src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:296`

**Issue:** `ActionParams.inactivitySeconds` exists in the Kotlin DTO (`Int?`), the TypeScript interface (`number?`), and is actively read by the controller at dispatch time (`p?.inactivitySeconds ?: 0` passed to `nullOperation`). However, no frontend code — neither `buildParams` in `ActionsPanel` nor any other component — ever populates this field. The `NULL_OPERATION` action therefore always receives `0` for `inactivitySeconds`, making any rules logic that depends on it permanently inert. Looking across all three layers, the full plumbing is in place but the top of the pipe is blocked. The UI review identified the unused TypeScript field; the cross-layer view confirms the Kotlin side is also effectively unused at runtime.

**Recommendation:** Either wire `inactivitySeconds` into the `ActionsPanel` UI (add an input control when the action is `NULL_OPERATION`), or remove the field from both `ActionParams` DTOs and the `nullOperation` signature until the feature is intentionally implemented. Add a `// TODO: wire UI control — NULL_OPERATION inactivity` comment at the controller dispatch site if the intent is to implement it later.

### [MEDIUM] `ResultMessage.details` is an untyped free-form string contract between the server result converters and the frontend NarrativePanel

**File:** `src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:338` and `frontend/src/components/NarrativePanel.tsx`

**Issue:** The server builds `details` as a human-readable string inside private extension functions (`OperationResult.toDispatch`, `AnalyzeHostResult.toDispatch`, `AnalyzeSecurityResult.toDispatch`, etc.). The frontend's `NarrativePanel` renders this string directly as narrative output. There is no structured type between the two: the string format is only an informal convention. Any server-side change to how `details` is assembled (e.g. changing `" — "` separators, reordering dice counts, adding new fields) silently alters what players read, with no compile-time warning on either side. Because the issue spans both the server's result-converter layer and the UI rendering layer, it is only visible in a cross-cutting view.

**Recommendation:** For the most commonly rendered result shapes, consider adding a structured companion to `ResultMessage` (e.g. an optional `outcome` sub-object with typed `deckerSuccesses`, `hostSuccesses`, and a `label` enum). This would let `NarrativePanel` format the narrative locally using the TypeScript type system, leaving `details` as a fallback for operations that do not fit a standard shape.

### [INFO] Server-review finding about `AvailableActionDto.actionType` redundancy is a misread — cross-cutting analysis shows the two fields carry distinct information

**File:** `src/main/kotlin/com/shadowrun/matrix/server/dto/AvailableActionDto.kt:15` and `frontend/src/types/messages.ts:75`

**Issue:** The per-part server review (pass_3_maintainability_server.md) classified `actionType` in `AvailableActionDto` as a [MEDIUM] finding, asserting it duplicates the `kind` JSON discriminator. Cross-cutting examination of `messages.ts` shows this is incorrect: the TypeScript side declares `type ActionType = 'FREE' | 'SIMPLE' | 'COMPLEX'` and every `AvailableActionDto` variant has `actionType: ActionType` — the action cost category (FREE/SIMPLE/COMPLEX turn cost). The `kind` field (`'LogonToRtg'`, `'Operation'`, etc.) is the structural discriminator for deserialisation. A typical JSON object therefore has `"kind": "Operation"` and `"actionType": "COMPLEX"` — two different values carrying different game information. The frontend `ActionsPanel` consumes `actionType` to communicate the action cost to the player.

**Recommendation:** Close the server-review [MEDIUM] finding about `actionType` redundancy — it is not redundant. No code change is required. If desired, add a brief comment in `AvailableActionDto.kt` clarifying that `actionType` carries the action-cost category (e.g. FREE/SIMPLE/COMPLEX) while `kind` is the discriminator, to prevent the same misread in future reviews.

## No Issues Found In

- WebSocket message framing — `ServerMessage` discriminated union in TypeScript fully covers all server-emitted types (`control`, `state`, `result`, `error`); the Kotlin side serialises exactly those four types and no others.
- `ErrorCode` serialisation contract — Kotlin `@SerialName` values (`"not_your_turn"`, etc.) match the TypeScript `ErrorCode` union literals exactly; the per-part reviews noted one in-server string-coupling issue, but the wire format itself is correct.
- `MatrixObjectDto` / `MatrixObject` mapping — the `kind` discriminators in TypeScript mirror the Kotlin `@SerialName` annotations faithfully; the server-review INFO finding about enum-to-frontend contract covers the remaining risk adequately.
- `DeckerStateDto` — fields mapped in `toDto()` align with the TypeScript `DeckerStateDto` interface; no phantom or missing fields.
- `ActionCommand` / `ActionParams` round-trip — apart from `inactivitySeconds` (noted above), all fields are used consistently across the three layers.
- Reconnect / session-token flow — the `reconnectToken` field travels correctly from `ControlMessage` through `useWebSocket.ts` into the next `JoinMessage`; no cross-layer inconsistency.
