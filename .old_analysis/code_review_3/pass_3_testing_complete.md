# Testing Review — complete (cross-cutting)

## Summary

Each individual layer has testing deficiencies that are significant on their own, but several more serious gaps only become apparent when reading all three parts together. The game-logic layer has zero tests for `Decker.availableActions()` and `Decker.visibleObjects()`, the server layer applies a `filterNot` on the action list and re-indexes it before broadcasting, and the UI layer has no test framework at all. The conjunction of these three absences means the complete action-selection round-trip — from `availableActions()` through the server filter and DTO index assignment to the client's `actionIndex` lookup — is entirely unverified at every stage and at every boundary crossing. Similarly, the reconnect-token flow involves all three layers (server issues the token, the UI stores and resends it, the game-logic decker state must survive the cycle) and is untested in every one of them. A third class of cross-cutting gap concerns the TypeScript types that manually mirror Kotlin enums: `QueryPrecision`, `IcBehavior`, `ActionType`, and `ErrorCode` are all maintained by hand, and none has a contract test that would catch a rename or addition on the Kotlin side. The most visible runtime consequence of these gaps is already present: `NarrativePanel` maps only 4 of the 7 `ErrorCode` values, a discrepancy that is invisible from within either the server or the UI alone.

## Findings

### [HIGH] Action-selection round-trip is untested across all three layers
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:44
**Issue:** The action-selection pipeline crosses all three layers and has no test at any stage of it. `Decker.availableActions()` (game_logic, zero tests per the game_logic review) produces a list of `AvailableAction` objects. The server applies `filterNot { SWAP_MEMORY, LOCATE_DECKER }` (line 45–46, untested per the server review), then calls `mapIndexed` to produce `AvailableActionDto` objects whose embedded `index` fields equal their position in the filtered list. The client receives those DTOs, displays them, and sends back `actionIndex`. The server resolves that integer with `availableActions.getOrNull(cmd.actionIndex)` (line 90) against the same filtered list. The entire chain — domain action list, filter, index assignment, wire serialization, TypeScript parsing, and server-side lookup — has no test that exercises more than one of these stages at a time. An off-by-one in the filter, a change to the filtering set, or a DTO mapping bug would all produce silent wrong-action dispatch: the client sees and selects one action, the server executes a different one.
**Recommendation:** Add an integration test that places a decker on a host (so `addHostSystemActions` adds SWAP_MEMORY and LOCATE_DECKER), runs the turn setup phase, asserts the received `StateMessage.availableActions` contains neither of those operations, and then sends back an `actionIndex` for a known action (e.g. `ANALYZE_HOST`) and asserts the `ResultMessage` reflects that operation. This single test would verify the filter, the index contract, the DTO serialization, and the server-side lookup simultaneously.

### [HIGH] Reconnect flow is untested at every layer boundary
**File:** src/main/kotlin/com/shadowrun/matrix/server/SessionRegistry.kt:56
**Issue:** The reconnect-token flow involves all three parts and is unexercised at each boundary. The server issues a `reconnectToken` in the initial `ControlMessage` (line 67 of `SessionRegistry`) but no test asserts the token is present in that message (server review). The TypeScript `useWebSocket` hook stores the token in `reconnectTokenRef.current` (line 95 of `useWebSocket.ts`) but never clears it on `ws.onclose`, so after a full session expiry the stale token is re-sent on the next join (UI review). The server's reconnect branch at lines 56–65 of `SessionRegistry` — which must validate the token and restore decker state — is never exercised by any test (server review). No game-logic test verifies that a decker's in-progress state (tally, location, loaded utilities) survives a disconnect/reconnect cycle. The three untested stages are individually noted in the per-part reviews, but together they mean the entire reconnect feature is a dead code path from a testing perspective.
**Recommendation:** Add an integration test that (1) opens a WebSocket, joins, and records the `reconnectToken` from the `ControlMessage`; (2) closes the connection; (3) opens a new WebSocket and joins with the stored token; (4) asserts the new `ControlMessage` has `reconnect: true` and no new token; (5) asserts the subsequent `StateMessage` reflects the same decker name and location. On the UI side, add a mock-WebSocket test asserting that `reconnectTokenRef.current` is `null` after `DISCONNECTED` when the token has expired (i.e., clear the ref in `ws.onclose` when the server sends no new token in the reconnect `ControlMessage`).

### [HIGH] ErrorCode rendering gap spans Kotlin serialization, TypeScript type, and NarrativePanel
**File:** frontend/src/components/NarrativePanel.tsx:3
**Issue:** This defect requires reading all three layers to see in full. The Kotlin `ErrorCode` enum (Messages.kt:17–25) defines seven variants with `@SerialName` snake_case values. The TypeScript `ErrorCode` union type (messages.ts:116–124) correctly lists all seven matching strings. However, `NarrativePanel.tsx` defines its own local `ERROR_LABELS` map with only four entries, missing `name_too_long`, `unknown_message_type`, and `bad_request`. When the server sends any of these three error codes, the UI falls through to the raw `ev.msg.message` value and displays the snake_case string to the user. The per-part UI review flags the NarrativePanel map, but the reason it is a cross-cutting issue is that the complete set of codes is only visible by reading the Kotlin enum: neither the TypeScript type alone nor the NarrativePanel alone reveals that three codes are unhandled.
**Recommendation:** Delete the local `ERROR_LABELS` map in `NarrativePanel` and import a shared map from `App.tsx` (which already correctly uses `Record<ErrorCode, string>` enforcing TypeScript completeness). Add a rendering test that dispatches each of the seven `ErrorCode` values as an error event and asserts a human-readable sentence appears for each.

### [MEDIUM] QueryPrecision string contract between TypeScript and Kotlin is unverified
**File:** frontend/src/types/messages.ts:11
**Issue:** `ActionParams.precision` in TypeScript is typed as `'VERY_VAGUE' | 'VAGUE' | 'NORMAL' | 'SPECIFIC' | 'VERY_SPECIFIC'`. On the server, `locateWithState` parses the string with `QueryPrecision.valueOf(it)` (WebSocketDeckerController.kt:314), which uses the Kotlin enum constant name — not a `@SerialName` annotation. No test verifies that the five TypeScript string literals match the Kotlin enum constant names. If a Kotlin refactor renames a variant (e.g. `VERY_VAGUE` → `VERY_LOW`), the server silently falls back to `NORMAL` for the mismatched string, the TypeScript type continues to compile, and no test fails. Only the game outcome is quietly wrong.
**Recommendation:** Add a contract test — either a Kotlin test that serializes each `QueryPrecision` value using `.name` and asserts the expected strings, or a CI script that extracts the enum constant names and diffs them against the TypeScript union literals. Pair this with a server integration test that sends each precision value and asserts the locate operation proceeds (verifying valueOf succeeds for all five).

### [MEDIUM] IcBehavior and ActionType serialized values are inlined in TypeScript without contract verification
**File:** frontend/src/types/messages.ts:53
**Issue:** The comment at line 53 of `messages.ts` documents five Kotlin enum mirrors that must be updated manually. Two of them — `IcBehavior` (inlined as `'PROACTIVE' | 'REACTIVE'` in `MatrixObjectDto`) and the action `ActionType` (typed as `'FREE' | 'SIMPLE' | 'COMPLEX'` in `AvailableActionDto`) — are not listed in the comment at all, making them invisible to maintainers performing a Kotlin-side change. Neither has a contract test. `IcBehavior` uses Kotlin's default `.name` serialization (no `@SerialName`), so any rename would silently produce an unknown string on the TypeScript side, causing the IcProgram card to show a raw constant name instead of the expected label. `ActionType` has the same risk.
**Recommendation:** Add both `IcBehavior` and `ActionType` to the manual-sync comment. Create a Kotlin contract test that serializes one `AvailableActionDto.Operation` with each `ActionType` and one `MatrixObjectDto.IcProgram` with each `IcBehavior` variant and asserts the expected string values, so a rename breaks the test immediately rather than silently at runtime.

### [MEDIUM] AvailableActionDto `index` field vs. server `getOrNull(actionIndex)` contract is implicit and untested
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:90
**Issue:** The server assigns `index` fields to `AvailableActionDto` objects via `mapIndexed` called on the already-filtered list (line 66 of `AvailableActionDto.kt`, called from line 44–66 of the controller). The client is expected to read this `index` field and echo it back as `cmd.actionIndex`. The server then calls `availableActions.getOrNull(cmd.actionIndex)` to resolve the action. The invariant — that the `index` field in each DTO equals the position of that action in the filtered list — is load-bearing but nowhere documented or tested. If a future change inserts a pre-filter mapping step, or if the client uses a different field as the action identifier, the lookup silently executes the wrong action. The fact that `Decker.availableActions()` is entirely untested (game_logic review) makes this invariant even more fragile, because no test establishes the baseline ordering that the index contract relies on.
**Recommendation:** Add a unit test that calls `availableActions().filterNot { ... }.mapIndexed { i, a -> a.toDto(i) }` on a known decker configuration and asserts that for every resulting `AvailableActionDto`, `dto.index == position in the resulting list`. Then add an integration test (see the HIGH finding above) to verify the full round-trip.

### [LOW] `LOCATE_DECKER` dispatch returns error string rather than being absent from the client's action list — gap is invisible per-layer
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:233
**Issue:** `LOCATE_DECKER` is filtered out of the available-actions broadcast (line 45–46) so a well-behaved client should never send an action with this operation. However, `dispatchLocateOp` still contains an explicit branch for it (line 233) returning `"LOCATE_DECKER requires a target Persona — not supported via WebSocket"`. This dead-code branch is only visible as an issue when comparing all three layers: game_logic adds LOCATE_DECKER to the host action list (Decker.kt:167), server filters it before broadcast, server still handles it in dispatch, and the TypeScript type `SystemOperation` includes `'LOCATE_DECKER'`. No test verifies that a client cannot reach this dead branch by sending an out-of-band `actionIndex` corresponding to an unfiltered list position. Because `availableActions()` has no tests, the positions of LOCATE_DECKER and SWAP_MEMORY in the unfiltered list are unknown, making it impossible to reason about what would happen if the filter were accidentally removed.
**Recommendation:** Once the `availableActions()` unit tests recommended in the game_logic review are in place, add a test that confirms LOCATE_DECKER and SWAP_MEMORY do not appear in the filtered broadcast list at any index, and that sending the raw unfiltered-list index for LOCATE_DECKER results in `ResultMessage(success=false)` rather than a successful dispatch.

## No Issues Found In

- `ErrorCode` `@SerialName` annotations in Kotlin match the snake_case TypeScript `ErrorCode` union type values exactly — no drift on that side of the contract.
- `SessionRole` Kotlin serialized values (`"observer"`, `"registered_decker"`, `"active_controller"`) correctly match the TypeScript `Role` type.
- `ResultMessage`, `StateMessage`, and `ActionCommand` field names are consistent between the Kotlin DTOs and the TypeScript interfaces — no structural mismatch.
- The `@JsonClassDiscriminator("kind")` on the sealed `AvailableActionDto` class and on the server-side `MatrixObjectDto` correctly matches the `kind` discriminator field used in the TypeScript discriminated union types.
- The `MatrixJson { encodeDefaults = true }` configuration ensures default-valued fields are always present on the wire; the TypeScript types that treat these as non-optional are therefore safe.
