# Architecture Review — complete (cross-cutting)

## Summary

The codebase is coherent within each layer but has three cross-cutting fault lines that are only visible when the three parts are read together. The most severe is the `ActiveIcon` inversion: the game engine directly calls into server-layer WebSocket code through what appears to be a pure domain callback — a finding that is HIGH in both the game_logic and server per-part reviews but escalates to CRITICAL end-to-end, because the game loop and the WebSocket transport protocol are now indistinguishably fused. The second fault line is the absent `paramKind` discriminator in `AvailableActionDto`: the chain from `Decker.availableActions()` through the DTO serializer to the TypeScript `ActionsPanel` carries zero signal about which operations require which UI controls, so the frontend maintains a hardcoded operation-name registry that can only be kept in sync by hand. The third is the `location` field in `DeckerStateDto`, which is a formatted display string the frontend reverse-engineers by parsing hardcoded prefix patterns — a silent coupling between the server's formatting decision and the UI's data model. Alongside these are two smaller but pervasive inconsistencies: `LOCATE_DECKER` and `SWAP_MEMORY` are generated by the domain layer, silently filtered by the server, and invisible to the UI, with the unsupported-feature signal scattered redundantly across all three layers; and `inactivitySeconds` occupies the DTO contract in all three layers while having no UI control to populate it.

## Findings

### [CRITICAL] ActiveIcon inversion fuses game engine and WebSocket transport end-to-end
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:37
**Issue:** `Decker` (package `decker`) implements `ActiveIcon` (package `game`) with a no-op body, and `WebSocketDeckerController` (package `server`) also implements `ActiveIcon` with a 120-line body that performs WebSocket I/O, JSON serialization (`MatrixJson.encodeToString`), `CompletableDeferred` coordination, registry promotion/demotion, and broadcast. When `Game.runCombatTurn` calls `icon.action(context, diceRoller)` on what it believes to be a domain participant, it is transparently triggering all of that server infrastructure. Viewed across all three parts: the game-logic layer defines the interface, the domain entity `Decker` holds a dead implementation of it, and the server layer provides the live implementation — meaning the game loop and the WebSocket protocol cannot be tested or evolved independently. Any unit test of `Game` that involves a real player turn must instantiate or mock the full `SessionRegistry`, `TurnCoordinator`, and `CompletableDeferred` stack.
**Recommendation:** Introduce a transport-agnostic `PlayerInputPort` interface in the game or `common` package, with a single suspend method that takes a `Decker` and returns a resolved `ActionCommand`-equivalent value object. `WebSocketDeckerController` implements this port. The game engine depends only on the port; `ActiveIcon` is removed from `WebSocketDeckerController`. `Decker` itself no longer needs to implement `ActiveIcon` at all — it is a domain value, not an active participant. This cleanly separates turn-input protocol from game execution and makes both sides independently testable.

### [HIGH] LOCATE_DECKER and SWAP_MEMORY are generated, filtered, and rejected across all three layers with no single source of truth
**File:** src/main/kotlin/com/shadowrun/matrix/decker/Decker.kt:167 and src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:44
**Issue:** `Decker.addHostSystemActions()` unconditionally adds `LOCATE_DECKER` and `SWAP_MEMORY` to the available-actions list (Decker.kt:167–174). The server then filters both out before broadcasting the state message (WebSocketDeckerController.kt:44–46). If somehow a client sent an action index resolving to either operation (e.g. a race condition or a client bug), `dispatchLocateOp` and `dispatchMiscOp` each return a failure string ("not supported via WebSocket"). The TypeScript side never sees these operations in `AvailableActionDto`, so `ActionsPanel` never renders them. The unsupported-feature decision is thus expressed three times: once as domain-level inclusion, once as server-level exclusion, and once as a dispatch-level error path — with no canonical place that says "these operations are not available in the WebSocket server mode." If a third operation were added that similarly needs special handling, a developer must remember to update all three sites.
**Recommendation:** Add a capability predicate to the server layer — e.g. a `Set<SystemOperation>` of server-unsupported operations that is applied once, at the point `availableActions` is built for the session, or a filter extension on `List<AvailableAction>` defined alongside `WebSocketDeckerController`. Remove the redundant inline filter at line 44 and the dead dispatch error paths for these two operations. The domain layer (`Decker.availableActions`) should continue to enumerate all game-legal actions; it is the server's job to advertise only what it can fulfil.

### [HIGH] AvailableActionDto carries no paramKind — UI must hardcode operation parameter knowledge
**File:** src/main/kotlin/com/shadowrun/matrix/server/dto/AvailableActionDto.kt:49 and frontend/src/components/ActionsPanel.tsx:26
**Issue:** `AvailableActionDto.Operation` serializes only `operation` (a raw string), `targetKind`, and `targetName`. It carries no signal about which parameters the operation requires. The complete chain is: `Decker.availableActions()` builds actions with no parameter metadata → `AvailableAction.toDto()` serializes them with no parameter metadata → TypeScript `ActionsPanel` receives `operation: SystemOperation` and must determine which UI control to render by checking the operation name against hardcoded lists (`needsPrecision`, `needsPasscode`, `needsScanner`, `needsEdit`). These lists are domain knowledge — they encode Shadowrun game rules about operation inputs — living entirely in the UI layer with no compile-time or test-time link to the Kotlin `SystemOperation` enum or `ActionParams` fields. Adding a new parameterised operation requires updating the Kotlin enum, the Kotlin DTO, the TypeScript type, and the four frontend predicate lists — with no tooling to catch a missed update.
**Recommendation:** Add an optional `paramKind: String?` field to `AvailableActionDto.Operation` (value set by the server, e.g. `"precision"`, `"passcode"`, `"scanner"`, `"edit"`, or `null`). The mapping from `SystemOperation` to `paramKind` is defined once in a server-layer function (co-located with `AvailableActionDto`). The frontend reads `paramKind` to decide which control to render, eliminating all four hardcoded predicate lists. This change also makes the `ActionParams` fields self-documenting: each field corresponds to exactly one `paramKind` value.

### [HIGH] DeckerStateDto.location is a formatted display string — cross-layer parsing coupling
**File:** src/main/kotlin/com/shadowrun/matrix/server/dto/DeckerStateDto.kt (location field) and frontend/src/components/LocationPanel.tsx:8
**Issue:** `DeckerStateDto.location` is typed as `String` in both Kotlin and TypeScript (`messages.ts:42`). The UI's `locKey()` function (LocationPanel.tsx:8–14) reverse-engineers the location's identity by stripping hardcoded prefix strings (`"RTG: "`, `"LTG: "`, `"PLTG: "`, `"Host: "`) to produce a lookup key into `visibleObjects`. This means the frontend is tightly coupled to the exact format string the Kotlin DTO layer produces for each `MatrixLocation` variant. There is no type-level contract enforcing this. If the Kotlin side changes how it formats any variant — even a minor wording change — `locKey()` silently returns the wrong key, the `visibleObjects.find()` returns `undefined`, and the location display goes blank with no error. This is a cross-cutting coupling between the server's DTO serialization, the wire format, and the frontend's data model.
**Recommendation:** Replace the `location: String` field with a structured DTO, for example `location: { nodeKind: 'RTG' | 'LTG' | 'PLTG' | 'Host' | null; name: string }`, or add a separate `locationObjectIndex: number | null` field pointing directly into `visibleObjects`. Either approach eliminates the string-parsing step in `locKey()` and makes the contract type-safe on both sides. The Kotlin `toDto()` extension already has full access to the `MatrixLocation` sealed hierarchy and can produce structured output with minimal effort.

### [MEDIUM] ActionParams.precision is a raw String contract with silent fallback across all three layers
**File:** src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:314 and frontend/src/types/messages.ts:11
**Issue:** `ActionParams.precision` is declared as `String?` in Kotlin and as a string union literal in TypeScript (`'VERY_VAGUE' | 'VAGUE' | 'NORMAL' | 'SPECIFIC' | 'VERY_SPECIFIC'`). On the server, the value is parsed with `runCatching { QueryPrecision.valueOf(it) }.getOrNull() ?: QueryPrecision.NORMAL` — meaning any unrecognized or misspelled string silently becomes `NORMAL` with no error sent to the client. There is no `@SerialName` or schema enforcement linking the TypeScript literal union to the Kotlin `QueryPrecision` enum. If a Kotlin enum variant is renamed or added, the TypeScript type is not updated, the client sends the old value, and the server silently uses `NORMAL`. This is the same unverified enum-name contract identified for `AlertStatus` et al. in the server per-part review, extended to a user-facing input parameter where the silent fallback can produce wrong game outcomes.
**Recommendation:** Add `QueryPrecision` to the set of enums verified by the integration or schema test recommended in the server review (to check that Kotlin enum names match TypeScript string literals). Replace the silent `getOrNull() ?: NORMAL` fallback with an explicit error response to the client when an unrecognized precision value is received, so mismatches surface visibly during development.

### [MEDIUM] inactivitySeconds occupies the DTO contract in all three layers with no UI to drive it
**File:** src/main/kotlin/com/shadowrun/matrix/server/dto/Messages.kt:54 and frontend/src/types/messages.ts:13 and src/main/kotlin/com/shadowrun/matrix/server/WebSocketDeckerController.kt:296
**Issue:** `ActionParams.inactivitySeconds` exists in the Kotlin DTO, the TypeScript interface, and the dispatch chain (`dispatchMiscOp` reads `p?.inactivitySeconds ?: 0`). The UI per-part review noted there is no UI control in `ActionsPanel` that populates this field, so it is always passed as 0 or omitted. `NULL_OPERATION` is therefore always called with 0 inactivity seconds. This is dead interface surface spanning all three layers simultaneously. Whether this is a planned-but-unimplemented feature or a remnant is unclear from the code.
**Recommendation:** If the game mechanic for inactivity seconds is not yet implemented, remove the field from all three layers (`ActionParams` Kotlin, `ActionParams` TypeScript, and the `dispatchMiscOp` read) until it is needed. If it is an intentional server-side-only default, add a comment in `dispatchMiscOp` explaining why the client never supplies it. Leaving unimplemented fields in the wire protocol creates maintenance confusion and grows the surface area of the unverified enum-name / field-name contract between Kotlin and TypeScript.

### [INFO] Wire-protocol discriminator naming is inconsistent — top-level messages use `type`, nested DTOs use `kind`
**File:** src/main/kotlin/com/shadowrun/matrix/server/dto/Messages.kt:1 and src/main/kotlin/com/shadowrun/matrix/server/dto/AvailableActionDto.kt:7
**Issue:** Top-level server→client messages (`StateMessage`, `ResultMessage`, `ControlMessage`, `ErrorMessage`) use a `type` string field as their discriminator. Nested DTOs (`AvailableActionDto`, `MatrixObjectDto`) use `kind` as their discriminator (`@JsonClassDiscriminator("kind")`). TypeScript mirrors this exactly: `ServerMessage` is a discriminated union on `type`, while `AvailableActionDto` and `MatrixObjectDto` are discriminated on `kind`. The split is functional but undocumented. A new contributor adding a nested DTO might use `type` by analogy with the top-level messages and produce an inconsistent wire format.
**Recommendation:** Add a brief comment in `Messages.kt` or `AvailableActionDto.kt` documenting the convention: top-level envelope messages use `type` to align with WebSocket framing conventions; nested polymorphic DTOs use `kind` to avoid clashing with any envelope `type` field if they are ever embedded in a richer envelope. Alternatively, standardize on one discriminator name throughout (requires a coordinated frontend change).

## No Issues Found In

- The `type` string field on all top-level messages is consistent and matches the TypeScript union discriminant exactly — the wire protocol for message routing is clean.
- `frontend/src/types/messages.ts` — the comment explicitly cross-referencing each Kotlin enum source (`AlertStatus ↔ com.shadowrun.matrix.network.AlertStatus`, etc.) is good practice and provides a clear maintenance signal.
- `AvailableActionDto.toDto()` mapper — the mapping from domain `AvailableAction` to wire DTO is complete, co-located with the DTO, and handles all variants without omissions.
- The `reconnectToken` round-trip (server issues token in `ControlMessage`, client stores it and re-sends in `JoinMessage`, server verifies in `SessionRegistry.receiveJoin`) is correctly threaded through all three layers with no gaps in the contract.
- `useWebSocket.ts` reducer — the inbound message routing and state transitions are complete and cover all `ServerMessage` variants defined in `messages.ts`.
